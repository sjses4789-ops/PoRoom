# PoRoom 냉정 진단 — 커뮤니티 사이트 + 온라인 작업실로서 보완할 점

작성: 2026-11-02 · 대상: 웹 PoRoom(poroom.kr) · 근거: 코드 전수 확인 + 이번 대화에서 발견한 실제 장애/버그

> **먼저 밝혀 둘 한계** — 실제 사용자 수·재방문율·동시접속·비용 같은 운영 지표는 제가 볼 수 없습니다.
> 아래 진단은 (1) 코드와 화면에서 확인한 사실, (2) 이번 작업 중 실제로 터진 문제, (3) 이런 서비스가 일반적으로 겪는 패턴을 근거로 합니다.
> 숫자로 확인이 필요한 항목은 "확인 필요"로 표시했습니다.

## 0. 한 줄 총평

**기능은 이미 넓다(방·뽀모도로·채팅·피드·도전·랭킹·알림·앱). 하지만 (1) "지금 사람이 있다"는 감각, (2) "내일 다시 올 이유", (3) 기록과 사람에 대한 "신뢰", (4) 사용자가 늘어도 버티는 "운영 기반" 네 가지가 약하다.**
기능을 더 붙이기보다, 이 네 가지를 메우는 쪽이 성장과 직결됩니다.

강점도 분명합니다. 카메라 없이 함께 집중한다는 컨셉, 웹소설·웹툰 작가라는 좁고 선명한 타깃, 챌린지·이벤트(공모전) 구조, 4개 언어 정보 페이지(SEO)는 경쟁 서비스(스터디윗미류, 단순 뽀모도로 앱)와 차별점입니다.

## 2. P0 — 지금 막지 않으면 나중에 크게 아픈 것

### P0-1. 기록(글자수·집중시간)의 신뢰성

**문제(근거)**
- 글자수는 사용자가 직접 입력합니다. `setDailyChars(roomId, date, chars)`처럼 **임의 날짜의 글자수를 직접 덮어쓰는** 서버 기능이 있고, 서버는 입력값을 그대로 믿습니다.
- 이 숫자가 곧 랭킹 점수, 챌린지 성공(1천자/5천자/1만자), 대결 승패, 관리자 이벤트(7점)가 됩니다. **조작할 이유가 생기는 구조**입니다. 한두 명이 부풀리면 정직하게 쓰는 사람이 손해라고 느끼고 떠납니다(커뮤니티에서 가장 치명적인 이탈 사유).
- 기록 공개 정책(shared/private/free)은 있지만, 기록이 "맞는지"를 판단할 수단이 없습니다.

**해결**
1. **이상치 자동 표시**: 하루 증가량 상한(예: 일 15만자 초과), 1분 안의 급증, 같은 숫자 반복 입력을 감지해 `의심` 플래그. 플래그가 붙은 기록은 랭킹에서 보류하고 관리자 목록에 올린다.
2. **기록 출처 구분**: `수동 입력` / `방 입력창(실시간 증가분)` / `데스크탑 자동 집계(검증됨)`. 랭킹·챌린지 탭에 "검증된 기록만 보기"를 둔다. 데스크탑 프로그램(현재 개발 중)의 자동 집계가 이 검증 경로가 됩니다.
3. **수동 덮어쓰기 제한**: 과거 날짜 수정은 하루 N회·최대 N일 전까지, 변경 이력을 남김.
4. **신고 → 기록 정정/무효 처리** 절차를 운영 문서에 명시.

### P0-2. 법무·개인정보: 방침과 실제가 어긋나 있다

**문제(근거)**
- 개인정보처리방침에는 "만 14세 미만 가입 제한"이 적혀 있는데, **가입 흐름(온보딩)에는 연령 확인이 없습니다**(닉네임·직업만 받음). 방침과 실제 동작이 다르면 문제가 됩니다.
- **이용약관 페이지가 없습니다**(코드에서 확인). 커뮤니티는 금지 행위·운영자 권한·콘텐츠 권리·제재 기준을 약관으로 정해야 신고·차단 조치의 정당성이 생깁니다.
- **탈퇴해도 로그인 계정(auth.users)이 남습니다.** 서비스 키가 없어 지우지 못했고, 이번에 "탈퇴 후 재가입 시 가입 화면만 새로고침되는" 실제 버그로 드러났습니다. 개인정보 삭제 요구를 완전히 충족하지 못할 소지가 있습니다.
- 채팅 사진·화면 공유(모자이크 프레임)·귓속말을 받으므로, 신고·열람 절차와 보관 기간이 문서로 설명되어야 합니다. (사진 30일 보관은 이번에 구현함.)

**해결**
1. 가입 화면에 **만 14세 이상 확인 체크 + 약관·방침 동의**(동의 이력 저장).
2. **이용약관·운영정책 페이지** 작성(금지 행위, 제재 단계, 콘텐츠 권리, 신고 처리 기간).
3. **서비스 키를 이미 확보했으므로**, 탈퇴 시 `auth.users`까지 삭제하는 서버 처리 추가(0073으로 재가입 복구는 임시 대응일 뿐).
4. 데이터 보관 기간 표(채팅, 사진 30일, 신고 기록, 접속 로그)를 방침에 정리.
5. 청소년 보호: `10대` 태그가 있으나 14세 미만 제한이므로, **미성년자가 섞이는 방의 이미지·쪽지 규칙**(성적 콘텐츠 신고 즉시 비공개)을 운영정책에 넣는다.

### P0-3. 측정·감시·테스트가 없다

**문제(근거)**
- `package.json`에 `test` 스크립트가 없고, 테스트 도구·CI 설정이 없습니다. 오류 모니터링(Sentry 등)도 없습니다.
- 그 결과, 이번 작업만 봐도 **사용자가 신고해야 발견되는 문제**가 반복됐습니다: 출석이 안 찍힘(조회 1000행 제한), 화면 공유 멈춤, 마감방 참여자 잔류, 채팅 반응칩 레이아웃, 가입 후 화면 새로고침.
- 어떤 기능이 쓰이는지, 어디서 이탈하는지 알 수 없어 우선순위를 감으로 정하게 됩니다.

**해결**
1. **오류 모니터링**: Sentry(무료 플랜) 또는 Vercel Observability — 서버 액션 실패, 실시간 연결 오류를 알림으로.
2. **핵심 지표 6개를 한 화면에**(관리자 페이지에 탭 추가): 일 가입자, DAU/WAU, **동시접속 피크**, **가입 후 24시간 내 방 입장 비율**, D1/D7/D30 재방문, 방당 평균 접속자. (이벤트 로그는 이미 `activity_logs` 등에 일부 있음)
3. **스모크 테스트 10개**(Playwright): 비로그인 둘러보기, 로그인 안내 팝업, 방 목록, 방 만들기·입장, 채팅 전송, 뽀모도로 시작, 초대 링크, 챌린지 참여 — GitHub Actions로 푸시마다 실행.
4. **"1000행 제한" 같은 반복 패턴 점검 목록**을 만들어 전수 확인(이미 `fetchAllPages`가 있으니 사용하지 않는 조회를 찾는다).

### P0-4. 확장성과 비용 — 지금은 문제없어 보여도 구조적 한계가 있다

**문제(근거)**
- [포룸] 페이지(웹)와 앱·데스크탑용 `/api/app/home`은 **`daily_records` 전체를 읽어** 방별 누적/이번 달 글자수와 개인 순위를 계산합니다. 사용자·기간이 늘수록 선형으로 느려지고 DB 부하가 커집니다. 랭킹 페이지도 같은 구조입니다.
- 화면 공유는 PNG 프레임을 **실시간 방송 채널**로 2초마다 보냅니다. 참여자 수 × 공유자 수 × 시간만큼 메시지가 늘어 Supabase Realtime 요금·한도에 직접 영향을 줍니다.
- Supabase 무료 플랜의 동시 실시간 연결 한도가 있습니다(확인 필요: 현재 플랜과 피크 동시접속).

**해결**
1. **집계(롤업) 테이블**: `room_stats(room_id, total_chars, month_chars)`와 `user_month_stats(user_id, month, chars)`를 기록이 쌓일 때(트리거) 또는 야간 배치로 갱신. 페이지는 집계만 읽는다 → 응답 시간이 사용자 수와 무관해짐.
2. 화면 공유: 주기 상한(예: 4초), 해상도 상한, **한 방 동시 공유 인원 상한**, 지원 방 크기 제한. 필요하면 공유 기능을 프리미엄/옵션으로.
3. **비용 알림**: Supabase 사용량 80% 도달 알림, 요금제 전환 기준(동시접속 N명, DB 용량 N%)을 미리 문서화.

## 3. P1 — 성장·재방문 (가장 큰 효과)

### P1-5. "지금 사람이 있는 방"이 보이지 않는다

**문제(근거)**
- 방 카드에는 **참여 인원(가입자 수)**, 누적 글자수, 이번 달 글자수가 보일 뿐 **현재 접속 중인 사람 수는 없습니다.** 실시간 접속이 이 서비스의 핵심 가치인데 목록에서 가장 중요한 정보가 빠져 있습니다.
- 기본 정렬이 **누적 글자순**입니다. 오래된 큰 방이 위에 있고, 지금 사람이 모이는 새 방은 묻힙니다. 신규 방문자가 처음 들어간 방이 비어 있으면 곧바로 이탈합니다.
- "전체/추천 방"이지만 추천 로직은 없고 단순 정렬뿐입니다. 태그 필터 칩이 40여 개라 신규에게는 오히려 부담입니다.

**해결**
1. 방 카드에 **`지금 N명 작업 중`** 배지(초록 점). 서버가 방별 presence를 주기적으로 요약해 `rooms.online_count`로 제공(실시간 채널에서 센 값을 1분 단위로 캐시).
2. 기본 정렬을 **`지금 활동순`**(접속자 수 → 최근 활동)으로. "누적 글자순"은 보조 정렬로.
3. 상단에 **"지금 들어갈 만한 방 3곳"**(접속자 1명 이상 + 내 직업/태그에 맞음) 고정 노출.
4. 필터 칩은 **자주 쓰는 8개만 먼저 보여주고 "더보기"**로 접는다.
5. 활동이 7일 이상 없는 방은 목록 하단 "쉬는 방"으로 분리.

### P1-6. 콜드스타트 — 사람을 같은 시각에 모으는 장치

**문제**
- 실시간 서비스는 **동시에 있는 사람 수**가 전부입니다. 상시 열린 마감방·새벽방만으로는 "비어 있는 방"이 되기 쉽습니다. 그러면 신규가 떠나고 다시 비는 악순환이 됩니다.

**해결**
1. **정시 세션**: 매일 정해진 시각(예: 21:00, 23:00, 새벽 5:00)에 `25분 × 4 포모도로 세션`을 방 단위로 연다. 시작 10분 전 알림, 세션이 끝나면 "오늘 함께 쓴 글자수" 요약. 같은 시간에 오면 사람이 있다는 약속이 생깁니다.
2. **호스트가 있는 정기 방**: 연재 작가·웹툰 작가 몇 명과 협의해 "OO와 함께 쓰는 금요일 밤" 같은 고정 방. 호스트의 지인이 초기 트래픽.
3. **시즌 이벤트**: 지금(11월)은 집필 챌린지 시즌입니다 — **"11월 한 달 5만자" 같은 월간 챌린지**를 열고, 이벤트 포스터 기능(이미 있음)으로 홍보.
4. 외부 유입은 웹소설·웹툰 작가 커뮤니티(플랫폼 작가 카페, 공모전 준비 모임)에 **초대 링크**(이미 구현)로 방 단위 유입.
5. 가짜 접속자(봇)는 쓰지 않는다. 한 번 들키면 신뢰가 무너집니다.

### P1-7. 재방문 장치가 사이트 안에 갇혀 있다

**문제(근거)**
- 알림(벨)은 구현했지만 **사이트에 들어와야만 보입니다.** 웹 푸시·이메일·메신저 연동이 없어 "오늘 쓸 시간입니다/같이 쓰는 사람이 있어요" 신호를 밖으로 보낼 수 없습니다. 습관 서비스에서 가장 큰 누락입니다.

**해결**
1. **Web Push**(PWA는 이미 있음): 정시 세션 시작, 귓속말 도착, 챌린지 마감 임박, 연속 출석 끊김 직전(저녁 9시).
2. **주간 리포트 이메일**(이미 알림으로 계산 중): 이번 주 글자수·집중 시간·연속 일수 + 다음 주 정시 세션 안내.
3. 앱(Flutter)은 FCM 푸시. 알림 설정(종류별 끄기)과 방해 금지 시간을 반드시 함께 둔다(끄기 어려우면 오히려 이탈).

### P1-8. 가입 직후 첫 5분

**문제(근거)**
- 가입 직후 [포룸]은 내 현황(모두 0)과 방 목록 40개 칩이 보입니다. "첫 뽀모도로를 돌리는 데까지" 안내가 없습니다. 초대 링크를 받은 경우만 바로 방으로 이어집니다.

**해결**
1. 첫 로그인 한 번만: 큰 버튼 **"지금 사람이 있는 방에 바로 입장"**(P1-5의 추천 방) + "오늘 목표 글자수 정하기" 1문항.
2. 첫 방 입장 시 **짧은 안내 3단계**(뽀모도로 시작 → 글자수 입력 → 채팅 인사) 말풍선.
3. 첫 24시간 목표: **가입 → 방 입장 → 첫 뽀모도로 완료**. 이 전환율을 P0-3의 핵심 지표 1번으로 둔다.

## 4. P2 — 제품 완성도·운영

### P2-9. 사람 사이의 관계가 없다
- 지금은 방 단위로만 만납니다. 친구·팔로우·"함께 쓴 사람" 목록이 없고, 쪽지는 방 참여자 카드에서만 보낼 수 있습니다. 습관 서비스는 **"내가 안 나오면 아쉬워할 사람"**이 리텐션을 만듭니다.
- 해결: ① 함께 작업한 사람 목록(최근 30일), ② 즐겨찾기한 사람이 접속하면 알림, ③ **책임 파트너**(서로의 주간 목표를 보는 1:1 짝), ④ 주간 "같이 쓴 시간" 카드.

### P2-10. 4개 언어와 사용자 풀
- 정보 페이지(가이드·FAQ)의 다국어 SEO는 유효하지만, **커뮤니티(방·채팅·피드)를 4개 언어로 열어 두면 풀이 쪼개져** 어느 언어 방도 비어 보입니다.
- 해결: 당분간 커뮤니티는 **한국어 중심으로 운영**하고, 외국어는 SEO·안내 중심으로 유지. 방 만들기에 **언어 태그**를 필수로 두고, 목록은 사용자 언어 기준으로 먼저 보여준다.

### P2-11. 랭킹 설계
- 누적·월간 글자수 절대량 순위는 **신규가 영원히 따라잡지 못하고**, 장르(장편 연재 vs 시·에세이)와 작업 방식(타이핑 vs 그림)에 따라 불공평합니다. 컷수/글자수는 직업으로 분리했지만 충분하지 않습니다.
- 해결: ① **주간 리그**(비슷한 수준끼리 묶어 주 단위로 승급/강등), ② **개인 기록 대비 성장률** 랭킹, ③ **목표 달성률·연속 출석** 별도 순위, ④ 순위 공개 범위 선택(비공개 가능). 챌린지 점수(1·2·3·5·7점)는 유지하되 상한을 두어 한 사람이 독주하지 않게.

### P2-12. 피드·휴식 게시판의 "빈 방 효과"와 신뢰
- 게시판이 비면 사이트 전체가 죽어 보입니다. 심사용 예시 데이터(`demo-data`)와 **운영자 글 일괄 게시 기능**은 현재 꺼져 있거나 관리자 전용이지만, 실제 사용자 글이 적을 때 이런 것에 의존하면 **신뢰·정책 위험**(광고 심사에서 인위적 콘텐츠로 보일 수 있음)이 큽니다.
- 해결: ① 예시 데이터 코드는 정리·제거, ② 운영자 글은 "운영자" 표시를 분명히 하고 소수·고품질로, ③ 피드 첫 화면에 **"오늘의 질문"**(예: "오늘 쓴 한 문장")으로 참여 문턱을 낮춤, ④ 방 안에서 쓴 글자수 달성 시 **원클릭 피드 공유**.

### P2-13. 수익 모델
- 광고(`ADS_VISIBLE=false`)와 프리미엄 배지(`TIER_BADGE_VISIBLE=false`)가 모두 꺼져 있어 **수익이 없는 상태**입니다. 비용(실시간·저장소·이미지)은 사용자와 함께 늘어납니다.
- 주의: **작업·집중 도구에 광고를 상시 노출**하면 핵심 가치(집중)와 충돌합니다. 광고를 쓴다면 [포룸]·[피드] 목록 같은 "쉬는 화면"에만.
- 해결: ① 무료 핵심 기능은 유지, ② 프리미엄 후보 = 상세 통계·연간 리포트, 방 정원 확대, 사진 보관 연장, 화면 공유 고화질, 테마, ③ 후원(원하는 작가 커뮤니티에는 효과적), ④ 이벤트·공모전 파트너십(포스터 노출). 먼저 **비용 구조**부터 숫자로 파악(월 고정비, 사용자당 변동비).

### P2-14. 방장·운영 도구
- 방장 기능(이름·색·초대코드·강퇴·방 삭제)은 있으나 **공지 고정·방 규칙·입장 승인제·금칙어·권한 세분화**가 얕습니다. 방이 커질수록 방장이 지칩니다.
- 해결: 방 공지/규칙 고정, 입장 승인제(비공개방), 채팅 느린 모드·금칙어, 부방장 권한 선택(삭제만/강퇴 포함), 방 활동 요약(주간).
- 관리자 쪽: 신고 처리 상태(접수/처리중/완료)와 **처리 기한**, 반복 신고 대상 자동 경고, 제재 이력(감사 로그).

### 기타 확인 항목
- **사진 EXIF(위치 정보) 제거 여부**: 채팅 사진 업로드 시 위치·기기 정보가 남는지 확인하고, 업로드 단계에서 제거(확인 필요).
- **모바일 웹 경험**: 뽀모도로·채팅이 백그라운드에서 끊기는 문제가 구조적으로 있습니다. 앱(진행 중)이 해결책이며, 앱 출시 전까지는 "PWA 설치 안내"를 보강.
- **다크 모드·접근성**: 웹은 다크 모드가 있으나 데스크탑·앱은 아직. 키보드 조작, 대비 점검.
- **백업·복구**: 관리자 전체 백업은 있으나 **복구 절차 훈련**(실제로 복원해 보기)은 확인 필요.

**7~12주 — P1~P2 (유지·확장)**
- Web Push + 주간 리포트 이메일
- 데스크탑 자동 집계로 "검증된 기록" 분리, 랭킹 주간 리그
